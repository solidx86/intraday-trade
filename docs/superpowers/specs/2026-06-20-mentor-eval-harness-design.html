Mentor Eval Harness — Design Spec

Full-fidelity evaluation of the intraday-trade-mentor skill, re-expressed in standard tooling.

DRAFT — for review LOCAL-ONLY instrument Date: 2026-06-20 Owner: Solid

1. Purpose & context

Build a full-fidelity eval harness for the intraday-trade-mentor skill that re-expresses its existing bespoke eval discipline (intraday-trade-mentor-skill/evals/evals.json) in Promptfoo, the industry-standard eval tool. This serves two slots of the AI-development skill plan at once:

  • Phase 0 — toolchain standup: stand up Promptfoo against a real, owned target.
  • Phase 1 — Track A case study: "an eval you designed," with an LLM-as-judge calibrated against your own human labels and a reported agreement rate.

The mentor grades against the private framework supplement (data/framework/framework-full.md) for exact parameter-level detail, degrading to a condensed public build when that mount is absent (SKILL.md:246). We are deliberately evaluating the full (private) build for fidelity — so this harness is a local instrument, not a clone-and-run public artifact.

Portfolio value is preserved the way the rest of the repo already works: harness/config public, framework + dataset private. The deliverable a reviewer sees is the public Promptfoo config + a written case study + a screen-shared promptfoo view — not a runnable clone.

6. Error handling & edge cases

ConditionBehaviour
Private framework mount absentFail loudly. v1 requires the full build; do not silently run the degraded build and mislabel results.
Missing ANTHROPIC_API_KEYClear error before any case runs.
Judge non-determinismGrader at temperature 0; accept residual variance; calibration treats the judge as one noisy rater vs the human label.
Image load failureCase errors explicitly (not a silent empty critique).
Cost3 vision cases × small N — negligible; no batching needed in v1.
Python 3.14 vs SDK wheelsIf the Agent SDK lags on 3.14, pin a pyenv 3.12 venv for the driver (per project memory note).

6.1 Execution & secrets

  • Local-only run. Both calls (driver + judge) hit the Claude API; the eval runs on your machine, never in GitHub CI (private framework + cost + non-determinism).
  • Key: a single root .env (gitignored) holds ANTHROPIC_API_KEY. The driver loads it via load_dotenv(find_dotenv()) (walks up to root); run Promptfoo from the repo root (npx promptfoo eval -c <path>) or pass --env-path .env.
  • CI unchanged: GitHub keeps running the deterministic, key-less pytest -q journal-schema validation. Optional future CI signal = commit per-case output fixtures and run Layer-1 structural asserts on them (no key, no framework).

7. Testing the harness itself

The harness is "correct" when it discriminates: the two graded cases have known, opposite ground truths, so a working harness must separate them.

  • CRM (loss) — must land D/F, flag long-against-downtrend + sector-RS contradiction, cite the relevant lessons, stop before reframe.
  • SMH (invalidation-exit) — must land A−/B+, recognise a disciplined invalidation cut (not a fear exit).
  • Missing 4-cell — must refuse to grade and ask for the missing input (short message, no grade).

If Layer 1 + Layer 2 both pass on all three and the judge's verdicts match your labels, the harness works and the agreement number is meaningful.

8. Success criteria (v1 "done")

  • The 3 cases run via the Agent-SDK driver at full fidelity.
  • Layer 1 (pytest) + Layer 2 (llm-rubric) both green and discriminating.
  • Judge calibrated against your labels, with a reported agreement rate.
  • A promptfoo view screenshot captured.
  • Written up as the Phase-1 Track A case study.

9. Risks & open questions

  • Agent SDK ↔ skill loading (headless): confirm the SDK loads the mentor skill and dynamically reads its references + private framework exactly as Claude Code does. Primary build risk.
  • Provider response shape: confirm the custom-provider contract Promptfoo expects (so llm-rubric receives clean output text).
  • Small calibration N: 3 (→6) cases demonstrate the method, not statistical robustness — state this explicitly in the writeup.
  • Eval staleness: audit each case's ground_truth against current SKILL.md before trusting it as a label (tokens already verified present; semantics still to confirm).
